# Fototeca — новая платформа

Витрина + админ-панель для Fototeca (фотокниги, выпускные альбомы).
Next.js 16 (App Router) + Tailwind CSS 4 + PostgreSQL (доступ через `pg`,
без ORM — см. «О базе данных» ниже). Визуальное направление — «Светлый»
(4-й вариант из макета), выбранное для финальной платформы.

## Что уже сделано

### Этап 1 — Каркас + витрина
- Каркас проекта: Next.js + TypeScript + Tailwind, шрифты Outfit (заголовки) +
  DM Sans (текст) через Google Fonts.
- Дизайн-токены (`src/app/globals.css`) — те же значения, что в макете
  (`Main4.dc.html` и др.), чтобы витрина 1:1 совпадала с утверждённым дизайном.
- Публичные страницы: `/` (баннер + каталог + статьи + футер), `/catalog`,
  `/catalog/[slug]`, `/articles`, `/articles/[slug]`.

### Этап 2 — Оформление заказа + загрузка файлов
- `/order/[slug]` (`src/components/order/OrderConfigurator.tsx`) — рабочий
  конфигуратор: выбор формата, тип обложки (Хит2/Тканевая/Экокожа/Комби —
  один уровень), число разворотов, форзацы/упаковка/экспресс, живой пересчёт
  цены.
- Загрузка файлов drag-and-drop с **двухуровневой валидацией**, как в плане:
  клиент сразу читает реальные пиксельные размеры файла и подсвечивает
  результат; сервер (`POST /api/upload`) обязательно перепроверяет каждый
  файл через `sharp` — размер в px и цветовой профиль (sRGB) — и только
  после этого сохраняет на диск в `storage/orders/{draftId}/{index}.jpg`.
- «Оформить заказ» реально сохраняет заказ в базу (клиент, заказ, позиция —
  см. Этап 4) и показывает настоящий номер заказа.

### Этап 3 — База данных + админ-панель
- PostgreSQL — вся витрина и конфигуратор заказа читают данные из базы
  (`src/lib/repo/*.ts`), не из захардкоженного файла.
- `/admin` — панель администратора, вход по паролю на `/admin/login`
  (сессия — cookie на 7 дней). Есть **две роли** (см. Этап 4 ниже):
  администратор (`ADMIN_PASSWORD`) видит весь раздел, производство
  (`PRODUCTION_PASSWORD`) видит только канбан-доску.
  - **Дашборд** (`/admin`) — статистика по заказам, баннеру, статьям, каталогу.
  - **Заказы** (`/admin/orders`) — журнал всех заказов с фильтром по статусу;
    карточка заказа (`/admin/orders/[id]`) — данные клиента, состав заказа,
    смена статуса.
  - **Производство** (`/admin/production`) — канбан-доска: Печать → Сборка →
    Обложка → Готово, по одной карточке на позицию заказа; кнопка переводит
    позицию на следующий этап (и когда все позиции заказа готовы — сам заказ
    автоматически переходит в статус «Готов»).
  - **Баннер** (`/admin/banner`) — редактирование текста и кнопок, публикация/
    черновик; изменения сразу видны на главной странице.
  - **Статьи блога** (`/admin/articles`) — список, создание, редактирование,
    удаление, черновик/публикация.
  - **Каталог** (`/admin/catalog`) — название, описание, цена «от», видимость
    позиции. Форматы и цены за разворот пока редактируются только в базе
    (`catalog_formats`, `cover_options`) — экран для них появится позже.
  - Остальные пункты меню (Клиенты, Роли, Настройки) показаны как «скоро».

### Этап 4 — Производственный модуль + роли
- Оформление заказа теперь реально сохраняется: `submitOrder` находит или
  создаёт клиента по телефону, генерирует номер заказа в формате легаси-
  системы (`2026000001` — год + порядковый номер), создаёт запись в `orders`
  и `order_items`, показывает клиенту настоящий номер.
- Журнал заказов и карточка заказа в админке — раздел «Заказы» выше.
- Канбан производства — раздел «Производство» выше; этап хранится в
  `order_items.production_stage` отдельно от статуса всего заказа, как в
  старой системе (заказ может состоять из нескольких позиций на разных
  этапах).
- Лёгкие роли без отдельной таблицы пользователей: второй пароль
  `PRODUCTION_PASSWORD` в `.env` — сессия с ним видит только
  `/admin/production` (`src/proxy.ts` перенаправляет с любых других страниц
  админки). Если `PRODUCTION_PASSWORD` не задан — эта роль просто недоступна.

### Этап 5 — Миграция из старой системы
- Последние 500 заказов и вся клиентская база (по номерам телефонов,
  найденным в старых записях) перенесены из zakaz.fototeca.kz.
- Старые заказы **не** втиснуты в новую структурированную схему заказов
  (`orders`/`order_items` со ссылками на каталог) — старый журнал слишком
  «свободнотекстовый» для этого (один текстовый блок на адрес+доставку+
  оплату+примечания, товары просто текстом). Вместо этого — отдельная
  архивная таблица `legacy_orders`, хранящая запись как есть.
- **Архив заказов** (`/admin/legacy-orders`) — только просмотр и поиск по
  номеру, имени, телефону или e-mail, с пагинацией.
- Скрипты миграции (переиспользуемые, для будущих повторных экспортов):
  `scripts/legacy/xlsx-to-json.py` (конвертирует выгрузку из старой системы
  в JSON) и `scripts/migrate-legacy-orders.ts` (грузит JSON в базу — см.
  «Миграция из старой системы» ниже).

### Этап 6 — Docker Compose для развёртывания
- `Dockerfile` (multi-stage, `output: "standalone"`) + `docker-compose.yml`
  (платформа + PostgreSQL, тома для базы и загруженных фото) + автоприменение
  схемы БД при старте контейнера. Подробная инструкция по разворачиванию на
  своём сервере — в **[DEPLOY.md](./DEPLOY.md)**.

## Что дальше (по плану `plan-novoy-platformy.md`)

1. Развернуть на реальном сервере по инструкции в `DEPLOY.md`.
2. Полноценные роли (клиент/дизайнер/касса) с отдельной таблицей
   пользователей — сейчас админ-панель различает только «администратор» и
   «производство» по паролю.
3. При желании — перенести остальную историю заказов (сейчас перенесены
   только последние 500) через `npm run db:migrate-legacy -- <файл> --all`.

## Запуск локально (разработка)

Нужен установленный PostgreSQL (локально или в Docker) и Node.js 20+.

```bash
npm install
cp .env.example .env      # укажите DATABASE_URL, ADMIN_PASSWORD и (опционально) PRODUCTION_PASSWORD
npm run db:migrate         # создаёт таблицы (безопасно перезапускать)
npm run db:seed            # наполняет базу стартовым контентом
npm run dev                 # http://localhost:3000, админка — /admin
```

## Сборка для продакшена

```bash
npm run build
npm run start
```

> Для шрифтов Google (Outfit, DM Sans) при сборке нужен доступ в интернет —
> единственная внешняя сетевая зависимость всей платформы. Если сервер
> полностью офлайн — заменить `next/font/google` на `next/font/local` с
> заранее скачанными файлами шрифтов в `src/app/layout.tsx`.

## О базе данных

Схема создаётся и читается обычным SQL (`db/schema.sql` + `pg`), а не через
Prisma, хотя `prisma/schema.prisma` тоже в репозитории — как читаемая
документация модели данных (ER-диаграмма), не как рабочий инструмент.
Причина: классический Prisma CLI при каждом `generate`/`migrate` скачивает
нативный движок-бинарник с серверов Prisma — хрупкая зависимость для
локального сервера, где интернет может быть ограничен или отсутствовать.
Обычный SQL и `pg` работают везде без сетевых обращений при сборке.

```bash
npm run db:migrate   # применяет db/schema.sql (idempotent, безопасно повторять)
npm run db:seed       # заполняет банер/статьи/каталог стартовыми данными
```

Если у схемы что-то меняется — правьте `db/schema.sql` и по возможности
синхронизируйте `prisma/schema.prisma` вручную, чтобы документация не отстала.

## Миграция из старой системы

Чтобы перенести заказы и клиентов из zakaz.fototeca.kz (или обновить архив
свежей выгрузкой):

1. В старой системе: «Журнал заказов» → «Экспорт» → «Excel файл (.XLSX)».
2. Превратить выгрузку в JSON:
   ```bash
   python3 scripts/legacy/xlsx-to-json.py путь/к/Заказы.xlsx /tmp/legacy.json
   ```
   (нужны `openpyxl` — `pip install openpyxl --break-system-packages`, если
   их ещё нет).
3. Загрузить в базу:
   ```bash
   npm run db:migrate-legacy -- /tmp/legacy.json
   ```
   По умолчанию переносятся последние 500 заказов (по дате) — этого
   достаточно для активной работы техподдержки; добавьте `--all`, чтобы
   перенести всю историю. Клиентская база строится из **всех** строк файла
   независимо от лимита заказов, поскольку постоянный клиент важен, даже
   если сам его давний заказ в архив не попал.

Скрипт безопасно перезапускать: номер заказа уникален, повторный запуск с
тем же или перекрывающимся файлом просто пропустит уже перенесённые записи.

## Админ-панель

- Пароль администратора задаётся в `.env` (`ADMIN_PASSWORD`) — обязательно
  смените его перед реальным использованием, значение по умолчанию в
  `.env.example` только для разработки. `PRODUCTION_PASSWORD` — второй,
  опциональный пароль для сотрудников производства (видят только канбан).
- Вход: `/admin/login`. Все страницы под `/admin/*` защищены (см.
  `src/proxy.ts`) — без сессии открывается только страница входа; с сессией
  «производство» — только `/admin/production`.

## Структура проекта

```
src/
  app/                    — страницы (App Router), включая /admin/*
  components/             — публичные компоненты витрины
  components/admin/       — формы админ-панели
  components/order/       — конфигуратор заказа
  lib/db.ts               — пул подключений к PostgreSQL (pg)
  lib/repo/*.ts            — запросы к базе (banner, articles, catalog, orders)
  lib/orders-shared.ts     — типы/лейблы заказов без импорта `pg` (для клиентских компонентов)
  lib/auth/session.ts      — проверка пароля, роли (admin/production) и сессии админки
  lib/content.ts           — типы + стартовые данные (используются seed-скриптом)
  proxy.ts                 — защита /admin/* (Next.js 16: proxy заменил middleware)
db/schema.sql              — DDL базы данных (источник истины)
prisma/schema.prisma       — та же модель как читаемая документация (не исполняется)
scripts/seed.ts             — наполняет базу стартовым контентом
```
