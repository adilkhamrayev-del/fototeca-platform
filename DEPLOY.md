# Развёртывание на своём сервере

Платформа разворачивается через Docker Compose: два контейнера — сама
платформа (`app`) и её база данных (`db`, PostgreSQL 16). Инструкция ниже
рассчитана на обычный Linux-сервер (Ubuntu/Debian) с root- или sudo-
доступом по SSH.

## 1. Установить Docker (если ещё не установлен)

Проверить:

```bash
docker --version && docker compose version
```

Если команды не найдены — на Ubuntu/Debian:

```bash
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER   # чтобы не набирать sudo каждый раз — перелогиньтесь после этого
```

Для других ОС — официальная инструкция: https://docs.docker.com/engine/install/

## 2. Скопировать код на сервер

Распакуйте присланный архив `fototeca-platform.zip` на сервере (или
склонируйте репозиторий, если вы положили код в git):

```bash
unzip fototeca-platform.zip
cd fototeca-platform
```

## 3. Настроить `.env`

```bash
cp .env.docker.example .env
nano .env   # или любой редактор
```

Обязательно смените:
- `POSTGRES_PASSWORD` (и повторите то же значение в `DATABASE_URL`)
- `ADMIN_PASSWORD` — пароль входа в `/admin`
- `PRODUCTION_PASSWORD` — пароль для сотрудников производства (можно
  удалить строку, если эта роль не нужна)

## 4. Собрать и запустить

```bash
docker compose up -d --build
```

Первая сборка займёт несколько минут (нужен интернет — платформа при сборке
подтягивает шрифты Google Fonts, это единственная внешняя зависимость).
База данных поднимется первой, схема применится автоматически при старте
`app` (это безопасно повторять при каждом перезапуске).

Проверить, что всё поднялось:

```bash
docker compose ps
docker compose logs -f app
```

Платформа будет слушать `http://<адрес сервера>:3000`.

## 5. Наполнить начальными данными (один раз)

Стартовый контент (баннер, статьи, каталог с ценами):

```bash
docker compose exec app npm run db:seed
```

## 6. Перенести заказы и клиентов из старой системы (если ещё не переносили)

Скрипт конвертации выгрузки (`scripts/legacy/xlsx-to-json.py`) использует
Python — запускайте его **на своей машине**, не в контейнере (в образе
платформы Python нет и не нужен):

```bash
pip install openpyxl --break-system-packages
python3 scripts/legacy/xlsx-to-json.py путь/к/Заказы.xlsx legacy.json
```

Затем занести получившийся `legacy.json` в контейнер и запустить перенос:

```bash
docker compose cp legacy.json app:/tmp/legacy.json
docker compose exec app npm run db:migrate-legacy -- /tmp/legacy.json
```

По умолчанию переносятся последние 500 заказов (по дате) и вся клиентская
база из файла; добавьте `--all` в конце команды, чтобы перенести всю
историю целиком. Команду безопасно повторять — уже перенесённые заказы не
задублируются.

## 7. Поставить платформу за реверс-прокси (рекомендуется)

Отдавать порт 3000 напрямую в интернет не стоит — рекомендация самого
Next.js: поставить перед ним nginx/Caddy для HTTPS, лимитов и защиты от
некорректных запросов. Проще всего — Caddy, который сам получает
сертификат Let's Encrypt:

```bash
sudo apt install -y caddy
```

`/etc/caddy/Caddyfile`:

```
zakaz.fototeca.kz {
    reverse_proxy localhost:3000
}
```

```bash
sudo systemctl reload caddy
```

(Замените домен на тот, что будет указывать на этот сервер.)

## 8. Резервные копии базы данных

```bash
docker compose exec db pg_dump -U fototeca fototeca > backup-$(date +%F).sql
```

Стоит добавить это в cron раз в сутки и хранить бэкапы отдельно от сервера
(например, скачивать их куда-то ещё).

## 9. Обновление платформы новой версией кода

```bash
# положить новый код поверх старого (или git pull)
docker compose up -d --build
```

Загруженные фото заказов (`storage/`) и база данных живут в отдельных
Docker-томах (`storage_data`, `pgdata`) — пересборка контейнеров их не
затрагивает.

## Известные ограничения

- Docker-файлы (`Dockerfile`, `docker-compose.yml`, `docker/entrypoint.sh`)
  написаны по официальному образцу Next.js для `output: "standalone"` и
  проверены здесь настолько, насколько это было возможно без самого
  Docker-демона (песочница Claude не даёт его запустить): приложение
  собирается в standalone-режиме без ошибок, нативный бинарник `sharp`
  трассируется в вывод сборки для нужной платформы, `docker compose
  config` подтверждает, что compose-файл синтаксически корректен. Сама
  сборка образа (`docker build`) и запуск контейнеров ещё не были
  прогнаны вживую — при первом реальном запуске на вашем сервере может
  понадобиться небольшая правка, если что-то пойдёт не так — присылайте
  вывод `docker compose logs`, разберёмся.
